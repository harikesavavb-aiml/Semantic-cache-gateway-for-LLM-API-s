# Evaluation suite

Measures how reliably the gateway's **matching stage** decides "is this new
question a duplicate of a cached one?" on public, human-labelled datasets,
and compares it against simpler baselines.

It reports the two numbers that decide whether a semantic cache is worth using:

| Metric | Meaning | Why it matters |
|---|---|---|
| **False-hit rate** | wrong hits / hits served | A wrong cached answer is worse than no cache. This is the safety metric. |
| **Duplicates caught** | true duplicates reused / all true duplicates | Savings. A miss only costs one extra LLM call. |

## What is compared

1. Cosine similarity, single threshold (best F1, and at 99% precision) - the typical setup
2. Cross-encoder re-ranker, single threshold (same two operating points)
3. Cross-encoder, **three-zone** (auto-hit / verify / miss), borderline treated as a miss
4. Cross-encoder, three-zone **+ LLM judge** on the borderline zone (`--judge`)

## Datasets

- **QQP** (Quora Question Pairs, via GLUE validation split) - real question pairs.
  **Likely contaminated**: the models here were trained on Quora duplicate data, so
  treat QQP as an optimistic upper bound.
- **PAWS** (labeled_final, test split) - adversarial pairs with high word overlap
  but different meaning. Out-of-distribution for these models, so the fairer test.
  Note it is Wikipedia sentences, not chat questions.

- **hardneg** (synthetic, generated by `hardneg.py`) - pairs built to test the failure mode that
  motivated the project: near-identical questions that ask for different things. Negatives come
  in four hard types plus an easy one, and results are broken down by type:

  | Type | Example |
  |---|---|
  | `entity_swap` | "capital of India" / "capital of Japan" |
  | `number_swap` | "refund within 30 days" / "within 60 days" |
  | `attribute_swap` | "price of the X1 laptop" / "weight of the X1 laptop" |
  | `polarity_swap` | "how do I enable dark mode" / "how do I disable dark mode" |
  | `unrelated` | different topics entirely (the easy case) |

  Every label is re-derived from an independent lookup table in the tests, and mutation checks
  confirmed the tests fail when a label or the formatting is deliberately corrupted.
  **Limits:** the language is templated and repetitive, different seeds draw from one finite pool
  (so they are not independent replications), and each hard type has only ~85-150 held-out pairs,
  so 95% intervals are about +/-8-10 points: large gaps are detectable, small ones are not.

## Run it

```bash
cd backend
pip install -r requirements.txt -r evaluation/requirements-eval.txt

python3 evaluation/run_eval.py --selftest                       # no models/network; checks the plumbing
python3 evaluation/run_eval.py --datasets hardneg --n 2000      # synthetic hard negatives; no API key, fast
python3 evaluation/run_eval.py --datasets qqp,paws --n 2000     # cosine vs cross-encoder
export GROQ_API_KEY=...                                         # only for --judge
python3 evaluation/run_eval.py --datasets qqp,paws --n 2000 --judge
```

Output goes to `evaluation/results/RESULTS.md` and `results.json`
(including seed, model names, and library versions). Judge answers are cached
in `results/judge_cache_*.json`, so re-runs do not repeat paid calls.

## Method (so results are trustworthy)

- Each dataset sample is split in half with a fixed seed. **Thresholds are chosen
  on the calibration half only; every reported number comes from the held-out half.**
- False-hit rates come with 95% Wilson intervals. With few hits served the interval
  is wide - read it before comparing rows.
- If the verification zone would need more judge calls than `--judge-limit`, the
  run stops instead of judging a subset (a subset would bias the result).
- If the data is cleanly separable, the two calibrated thresholds coincide and
  there is no verification zone. That is correct behaviour, not a bug.

## Decision rule for `hardneg` (written before any real result was seen)

The cross-encoder design is **supported** on `hardneg` only if, at each method's best-F1 operating
point and with similar paraphrase reuse (within about 5 points), the cross-encoder's wrong-reuse
rate is clearly lower than cosine's (95% intervals do not overlap) on **at least three of the four**
hard types: `entity_swap`, `number_swap`, `attribute_swap`, `polarity_swap`.

Otherwise the honest conclusion is *no demonstrated advantage on this failure mode*, and the next
step is a mitigation (for example a rule-based guard that refuses reuse when the two questions
contain different entities or numbers), followed by re-measuring. Do not move the goalposts after
seeing the table.

## How to interpret results honestly

The claim this project wants to make is: *cross-encoder re-ranking plus selective
verification serves fewer wrong answers than cosine-only caching at comparable
savings.* That claim is **supported** only if, on PAWS (and ideally additional
datasets and seeds), the false-hit-rate intervals for the cross-encoder rows sit
clearly below the cosine rows at similar "duplicates caught". If they overlap, the
honest conclusion is "no demonstrated advantage" - report that rather than
cherry-picking an operating point.

## Limitations

- Evaluates pair classification, not the full gateway (no conversation history,
  no cached answers, no TTL/policy effects).
- The LLM judge here is a proxy: it compares two questions, while the gateway's
  production check also sees the cached answer.
- One seed and one sample per run; cross-dataset threshold transfer is untested.
- Does not yet include an external baseline such as GPTCache; adding one is the
  most valuable next comparison.

## Tests

`pytest tests/test_eval_metrics.py` checks the metric math against hand-computed
cases. These verify the *evaluation code*, not model quality.
